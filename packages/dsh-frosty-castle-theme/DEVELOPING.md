# Developing DSH Frost

The client uses the theme override layer and an additive shell overlay; all ornament CSS is scoped by dsh-core. The active artwork consists of `assets/rail.png`, `assets/side-rail.png`, `assets/junction.png`, `assets/crest.png`, and `assets/panel.png`, embedded because client bundles have no static-asset URL contract. Side rails have separately generated downward-pointing ice, rather than rotating horizontal icicles. Each frame edge extends 1px plus its corresponding `borderOffsetTop/Right/Bottom/Left` beyond the clipped viewport; unset edge values inherit the legacy `borderOffset`. Displacements are 0–48px, with defaults of 9/12/9/12px (top/right/bottom/left); an explicitly saved legacy offset remains the fallback for unset edges. Large offsets can hide artwork. The overlay does not intercept clicks or reflow content and can obscure edge controls.

The default-on `compatibilityInset` is an unsupported guarded Web-only patch, pinned to runtime release 0.2.1-rc.2 commit 332895e and its exact layout structure. For each edge it computes an automatic base of max(0, width − that edge’s displacement), adds each saved per-side adjustment (−48 to 96), clamps each final inset at zero, restores styles on disposal, and suspends itself while the right panel is open; it fails closed for other builds and desktop. This cannot replace an upstream composable four-edge inset API.

Large container surfaces, such as the collapsible page inset section and composer card, use stone border-image frame styling with corner caps and bevelled edges. They must not reuse the textured input or card fill (`--dsw-specific-input-major`, `--dsw-alias-settings-card-fill`): the controls inside then lose their contrast. Reserve textured fills for small controls.

For future theme artwork, prefer native transparency; if unavailable or unsuitable, generate against a uniform distinct key color and remove it carefully. Inspect the actual alpha over light, dark and saturated backgrounds before embedding; preserve the opaque iron and fine ice rather than keying by brightness. The general workflow is in the dsh-plugin-dev skill.

The frame width is the `--fr-width` CSS variable, set on the overlay from the accepted `borderWidth` (default 48px). The frame uses separately repeated rail spans and corner and crest junction images. Junction arms have different source band thicknesses, so CSS normalizes their horizontal and vertical scales against the rail band (106px versus 143px and 131px for the corner, and 113px for the crest). Their transition masks blend over the rail; this is a prototype and the generated textures are not a perfect match. This keeps the ornament visible while limiting overlap with controls at the window edges; the overlay does not reflow the shell. The browser slightly rescales repeated edge tiles to fill each side; ornaments within an edge tile are not independently fixed.

## Controls

Buttons, text boxes, menus, dialogs, tooltips and switches are restyled only through `ctx.theme.overrideTokens`, never by targeting DSH's hashed CSS-module class names. Each token in `TOKENS` is one DSH's own stylesheets already read; before adding one, check how DSH consumes it. `--dsw-corner-shape` set to `bevel` gives every rounded DSH surface its carved corners (Chrome 139 and later; other browsers keep rounded corners).

Textured background values are used for `--dsw-specific-input-major`, `--dsw-alias-button-elevated-fill` and `--dsw-alias-settings-card-fill`; these depend on current DSH stylesheet consumers and are not a documented component-material API. Re-audit them on DSH upgrades. The shared base and sidebar tokens must stay colors: DSH uses them in `background-color` and gradients. Preserve DSH’s shared menu material and blur. `--dsw-alias-button-primary-fill` must stay a plain color because DSH also uses it as a border color.

Per-control artwork, like the frame's, would need DSH to let a theme style individual controls; the token layer cannot. A sustainable upstream interface would provide lifecycle-managed surface materials (separate from color-valued aliases) and composable reactive safe insets on all four sides. DSH would own reflow and edge-anchored overlays; Frost's top inset would need to account for the crest, approximately 1.375 times the selected width. `shell.overlay` does not reserve space, while the single `shell.bottom` slot cannot provide four-edge clearance.

## Border width setting

`index.js` declares a volatile `borderWidth` in the Host Config (whole number, 12 to 48, default 30) and turns off Settings' generated form with `settings.configure({ auto: false })`, because Frost ships its own page. A Config or dependency change needs a server restart; a `client.js` change only needs a page reload.

The client reads the shared form from `ctx.configForms.get('dsh-frosty-castle-theme')` (the patch row id). The frame subscribes to it through `useSyncExternalStore`; the form's methods use `this`, so they are wrapped, not passed detached. The page registers on `plugins.row.config` with key `@rs-dsh/dsh-frosty-castle-theme#dsh-frost`, only while the Host serves that entry, and uses DSH's `SettingsFormModel` and `SettingsForm` (from `rsDshCore.ui`) so edits stay staged until Save, which sends one revision-fenced write. The draft parser rejects values outside 12 to 48, so a bad value disables Save instead of reaching the Host; the schema rejects them again on the Host. `WIDTH` in `client.js` and `BORDER_WIDTH` in `index.js` must match, and a test checks that.

Run `pnpm --filter @rs-dsh/dsh-frosty-castle-theme test`. For real UI verification use a separate DSH_HOME and port as described in the plugin development skill.
