# Developing dsh-cockpit

The reference for working on the plugin: its files, tools, routes, store, drift runner and web GUI rules. For what it does and how to set it up, see [README.md](README.md). The design and the project decisions are in [issue #1](https://github.com/romany-saad/dsh-plugins/issues/1). This file stays in the repository and is not published to npm.

## Build and test

```sh
pnpm test
node client/build.mjs   # after changing client/src, lib/rows.js or lib/present.js
```

`pnpm test` runs with network access blocked (`test/no-network.mjs`). A test fails when the committed `client/client.js` is not what the sources build.

To try a checkout, install it by path into a scratch profile: `dsh plugin --profile scratch add ./packages/dsh-cockpit`.

## Files

- `index.js`: the host plugin. Registers `board_open`, `board_read`, `board_add`, `board_update`, `board_inbox` and `board_process` inside `ctx.inject(['tools'], …)`, with `defineTool` from `@deepseek-ai/dsh-tools`. When the system-prompt service is present it also contributes one section, `rs-dsh:cockpit` (order 2850), from `guidance()`. It has two parts. `PLANNING` says to open a board, or keep the bound one, and to add the steps before starting multi-step work, and not to keep `todo_write` alongside it. It also says that one-step requests need no board and that a subagent reports to its parent instead of opening a board. `INBOX` says a note for later goes to the Inbox with `board_inbox`, unrefined, while the current work goes on. `UPKEEP` covers keeping a bound board current. With `skills` present it registers the `cockpit-refine` and `cockpit-process` skills (`skills/cockpit-refine.md` and `skills/cockpit-process.md`) through `ctx.skills.register`, for both the model and `/cockpit-*`; `tools.enabled: false` registers no skill either. `planning.enabled: false` drops `PLANNING` and restores 0.3's "do not open a board solely because of this guidance". The planning rule has to apply before any board exists: in 0.3 the section only spoke to sessions already using a board, so agents planned with `todo_write` and never opened one (#29). This is advisory, not automatic reconciliation; a complete custom prompt can suppress the section. The tool descriptions also say when to use each tool. Every agent in a profile that loads the plugin sees the tools; `tools.enabled: false` registers neither tools nor guidance.
- The per-turn context `rs-dsh:cockpit-context` (order 125, `interpolate: false`) is registered beside the section. DSH resolves a context's `text` synchronously and then interpolates it, so `text` must return a string, never a Promise (an `async` function failed every turn with `text.indexOf is not a function`). It reads `sessionBoards`, a per-session cache that the tools update after each write and that the `system-prompt/assemble` listener refreshes from the board file on every assembly, so a change made outside the session shows too. It lists in-progress, ready and waiting tasks, and the board's problems: `problems()` from `lib/rows.js`, at most `PROBLEM_LINES` (5) and then "and N more", under a line that says to fix only what is actually wrong and leave what looks intentional (the same rule is in `UPKEEP`).
- `lib/tools.js`: the tool bodies. Results are `{ ok: true, … }` or `{ ok: false, code, message }`, with the codes `not_bound`, `item_exists`, `item_unknown`, `unknown_reference`, `invalid_input`, `board_unreadable` and `write_failed`.
  - `board_open({ key, parent? })` creates or opens a board and binds the session to it, in memory and in `sessions/<sessionId>.json`, so a resumed session finds its board without reopening it.
  - `board_read({ item?, status?, checkDrift? })`: the tasks, the tree text, the flags, the last drift result, and the file's path and format version. The filters narrow the result only. `checkDrift: true` first runs the drift command (see Drift runner), and `driftCheck` says `ran`, `failed` or `not_configured`.
  - `board_add({ item?, what, status?, … })`: `item` defaults to the next integer, `status` to `next`. A field it does not know is refused (`invalid_input`); `extra` keeps anything else. A `parent` or `dependsOn` item not on the board is refused (`unknown_reference`): the task is defined first, then linked.
  - `board_add` and `board_update` take `refines` (Inbox ids) and `refinedWith` (a skill name): the items become `refined`, gain the task items in `refinedInto`, and are written with the task in one write. An unknown id is `unknown_reference`, a dropped one `invalid_input`; linking an item again to the same tasks changes nothing.
  - `board_inbox({ action, id?, text?, note?, source? })`: `add` (the next `iN`, never reused: `inboxSeq` on the board records the last), `update`, `drop`, `reopen`, `clear` (sets `clearedAt`; open items are refused) and `delete` (returns `previous`). With no board bound, `add` opens one with the key `defaultBoardKey(sessionId)` (`session-` and 8 characters of the id) through `board_open`, and the result has `opened`. Other actions then answer `not_bound`.
  - `board_process({ action, map?, kinds?, stages?, sources?, approved? })`: `read` returns the project process map from `.dsh/cockpit/process.yml` (or null); `propose` validates draft stages without saving; `save` requires `approved: true` and writes the YAML file atomically, bumping the revision and recording it on the board.
  - `board_update({ item, set? | remove? })`: `item` is one item or a list, changed in one write; one unknown item refuses the whole call (`item_unknown`), as does a `parent` or `dependsOn` in `set` that names no task on the board (`unknown_reference`). `null` in `set` clears a field. It returns `tasks` (after) and `previous` (before); a removal returns the removed tasks in `previous`, so `board_add` can put them back.
- `lib/route.js`: the read routes for the Board tab and the strip, `GET` and `HEAD` only, registered inside `ctx.inject(['connection'], …)` as exact Fetch routes on the host connection, which answers 403 to any Peer that is not the owner. Nothing registers on the raw web server. `route.enabled: false` registers none.
  - `/api/dsh-cockpit/boards`: `{ boards }`, the keys in the folder.
  - `/api/dsh-cockpit/board?key=K`: the board file as stored; 404 for an unknown key.
  - `/api/dsh-cockpit/view?sessionId=S`: `{ key, board, tree, flags, problems, driftConfigured, links }` for the session's bound board, `links` being the profile's non-empty link patterns, else `{ key: null, boards }`. A bound board that is missing, unreadable or cannot be drawn comes back as `{ key, error }`. An unexpected read error is a 500 that names its code, not its paths.
- `client/client.js` (`./client`, `dsh.client` with `platform: 'web'`): the Board tab in the web GUI's right sidebar, read-only. Built from `client/src/panel.js`, `client/src/command-box.js`, `client/src/segments.js` and `client/src/graph.js` by `node client/build.mjs`, which inlines `lib/rows.js`, so the tab and the tree text share their rules; a test fails when the committed file is not what the sources build. The tab polls the view route every 2 s and shows:
  - a header with the key and parent, the revision and time, and the drift line ("Drift: 1 differs · 16:40") when drift is configured or has run;
  - **Needs you**: its title is a button (`data-needs-you-toggle`) that hides or shows the cards; hidden, the section is one line with the count. The choice is `needsYouHidden` in `localStorage['dsh-cockpit.view']`, with `mode` (`list` or `graph`), per browser, not per board. Shown, one card per open task whose `waitingOn` is `user`: the title and an "Open PR" link on one line, then its next action as written and the ready command with Copy, both spanning the card. The step id is in the title's tooltip;
  - **Board data problems**, each naming its reference, with ↓ to the row;
  - **Inbox**: one card (`.dshc-ibcard`, a step group's border and radius): a header in the group title's tint with the title, the open count and Refine all, the items as rows with dividers, and Add item… as the last row; the note on what a button did goes under the card. The items not cleared, with "refined → 12, 13 · with grill-me", "dropped" and the note. **Refine** (open items), **Refine all** (two or more open), **Clear** (refined or dropped) and **Add item…** call `useFill`, which puts `/cockpit-refine i3`, `Clear inbox item i2.` or `Add to the inbox: …` (`inboxPrompts` in `lib/inbox.js`) in the session's message box through the slot's `inputActions.setDraft`. With `inbox.sendOnClick` (default true; the view answer carries it as `inboxSend`) the three fixed requests are then queued with `inputActions.submit('queue', 'click')`; Add item… always only fills, because the user types its text. `useFill` never replaces or sends a draft, and refuses while a message is mid-submission, but messages already waiting in `input.queue` do not block it: the click goes behind them. It says what happened under the section ("Queued for the agent.", or why not). Without `inputActions` the section shows no buttons. The empty state (no board) also has Add item…;
  - a view bar: **List | Graph** (`data-view`), and **Compact | Expanded** when a task has a flow (list only);
  - **Whole board** (`Overall`), the first card in `.dshc-groups`, before the sections: the count and bar, the strip's own model (every leaf task, parents not counted again, in the order the sections below draw them: `boardGroups` in `lib/rows.js`), and a key (`data-legend`) counting each segment kind present. It has a parent header's border, padding (10 px each side) and bar box, so its bar's edges are the group bars' edges at any width; a parent header with a chevron keeps the same 10 px right padding for this;
  - in Graph mode, the Whole board card, then `GraphView`: `graphLayout` (`client/src/graph.js`, import-free and inlined) draws each task with children as a container (`.dshc-gc`, `container: true`): a box at the full width it is given, its header (30 px) the parent's mark, title and count, its children laid out inside with 8 px padding, nesting for deeper parents. A parent loop is cut at the step that closes it. Within one box, or at the top, siblings go in layers by the longest path over `dependsOn`, a dependency inside another box counting as that box, a cycle cut at the step count; leaves fill columns of at least 132 px and wrap, each row centred, a box taking a row of its own. Only dependencies are lines (dashed, over the boxes, under the steps); the boxes show the parents. A parent's `dependsOn` on one of its own descendants is implied and gets no edge (`inside` in `graphLayout`), so `graphFocus` does not light it either; it is still in the layout's ranking within the box, which changes nothing since a box's children are drawn inside it. Pointing at a node or focusing it (`onPointerEnter`/`onFocus`) sets `data-focus` on the box: `graphFocus` lights the node (`data-lit=self`), the steps it depends on (`dependency`) and the steps that depend on it (`dependant`), one `depends` edge each way (parent edges are not followed), and those edges; the rest dims to 30 % (edges 15 %), with no transition. A click pins the highlight (`pin`, `data-pin`, `aria-pressed`, a 2 px info outline): while pinned, hover changes nothing; a second click on the same node, a click on the graph outside any node or box, or Escape clears it, and a click on another node moves it. Enter or Space on a focused node pins too. A double-click switches to List and focuses its row. The other way, a double-click on a list row (`onGraph`, not on a link, a button, a segment, the detail or a command box) sets `graphPin` in `BoardView` and switches to Graph: `GraphView` (keyed by the pin, so it starts afresh) takes it as `initialPin`, starts pinned there and scrolls the node to the centre once measured. The **List | Graph** switch clears `graphPin`. The row's two clicks have toggled its details twice by then, so they end as they were. The line beside the key (`data-graph-hint`) says which applies. While lit, a dependency line animates (`dshc-flow`: `stroke-dashoffset` 0 to -7, one "4 3" dash period, 0.5 s linear): each path starts at its dependency and ends at the step that waits, so the dashes run that way. It is the board's only motion, and off under `prefers-reduced-motion: reduce`;
  - in Agents mode (`mode: 'agents'`), `AgentsView` in place of the steps: the session's subagent tree as DSH's header dropdown (ui-subagent's `CatalogDropdown`) lists it, which DSH does not export. It reads what that dropdown reads, from the tab slot's standard props: `useSessions` (`projectionsBySession[id].values.subagentCatalog` per Session, `byId` for titles, `tokenUsage` and `subagentTiming`) and `useSessionStatus` (live running state first). `agentCatalogOf` derives each catalog's state as ui-subagent does. The root catalog loads only when asked, so the view calls `agents.refresh(sessionId)` once, then `agentBranchesToLoad` each agent whose own catalog is not loaded, once per mount, skipping external tasks and folded branches; live projection frames keep loaded levels current. `apply` passes `agents: { open, aside, refresh }` through the tab slot's `inject`: `uiWorkspace.openSession(address)`, `sidebarRight.openResource('dsh-resource://subagentchat/session/<child>?parent=<parent>&mode=<mode>', { kind: 'subagentchat', preferNewPane: true })` and `sessions.refreshProjections(id)`, the dropdown's own addresses. Each row's model line is `agentModel`: the child's own `modelSelection` projection (`lastUsed`, else `next`), as DSH's agent-team rows read `projectionsBySession[id].values.modelSelection`, written "<model> · <effort>" with the provider in the tooltip; none for external tasks or before a selection is recorded. The dots are the host's `StateDot` (`ongoing`, `done`, `idle`), drawn when the shell has none. Running keeps an entry that runs, or has a running agent anywhere under it in the loaded catalogs (`agentShown`, `agentRunsBelow`); a kept entry that is not running itself gets `data-agent-context` and its row is dimmed. The Running / All choice is `agentsFilter` in `localStorage['dsh-cockpit.view']`. Without `useSessions` (outside DSH's web app) it says so;
  - the step menu: `BoardBody` calls the tab slot's standard `useContextMenu` (dsh-client-ui-context-menu's prop, absent without it) and passes `menu` down. List rows (the `li`, parents too) and graph nodes and boxes spread `menu.getTriggerProps(target, handlers)`: right-click, Shift+F10 and the ContextMenu key open DSH's menu. A graph box passes its own Enter/Space pin handler through `handlers`, so it runs first. `target` is read when the menu opens: `stepTarget` returns `{ kind: STEP_TARGET, value }`, `STEP_TARGET = 'dsh-cockpit.step'`, a frozen JSON value (sessionId, boardKey, item, what, title, status, parent, issue, issueUrl, pr, prUrl, readyCommand, view), only `http(s)` links. It is a public contract for other plugins; adding a field is fine, renaming or removing one is breaking. `apply` registers cockpit's own contribution `dsh-cockpit.copy` (order 10) inside `ctx.inject(['contextMenus'], …)`, so the plugin still loads without the service: `stepCopyActions` gives the copies, then the links after a divider. A copy uses `copyText` and throws when it fails, so DSH's menu shows the action's `failureLabel` in a toast. `copyText` (`client/src/command-box.js`, also behind every Copy button) tries `navigator.clipboard.writeText` first; that API exists only in a secure context (HTTPS or localhost), so where it is missing or refuses, `copyWithTextField` copies through a hidden read-only `textarea` and `document.execCommand('copy')`, which browsers still allow from the click itself, then removes the field and gives focus back;
  - each root parent and its subtree in a separate bordered section, then a **Standalone tasks** section for roots without children. The parent row is the section's header: its title with the count on the same line ("0 of 3 done · 1 needs you", dropped counted apart), and under them a segmented bar spanning the section, one segment per direct child. The chevron column only shows when the parent has details to open;
  - the task rows in tree order, in columns mark · title · PR · chevron. The status is the mark only: one 12 px circle per status in DSH's StateDot `step` style (a 1.5 px ring, `corner-shape: round` against DSH's default squircle), shaped like the status's bar segment, so a row and its bar read the same. Done is the host's filled step with its check; now is a ring half filled with the info accent (still, not the host's spinner); waiting is filled grey, or orange when it needs you; next is an empty ring, green when ready and dashed grey when blocked, as its segment's border (`nextReady`; its tooltip and accessible name "next · ready" or "next · blocked"); dropped is a ring with a dash, its title struck through. Its word is the mark's tooltip and accessible name. The step id is in the title's tooltip and the expanded detail, so neither takes a column. When the segments do not fit, or above 24, the bar is one continuous bar of runs (`stackRuns` in `client/src/segments.js`): one run per kind present, in `RUN_ORDER` (done, now, needs you, waiting, ready, blocked, dropped), widths by largest remainder filling the bar exactly, each at least 2 px when there is room.

The styles use the host's tokens (`--dsw-alias-*`, `--dsw-radius-*`) and follow its Tag pill, small outline Button and sentence-case section titles; text colours keep the 4.5:1 light-theme mixes above.

- `cordis.patch.yml`: the bundle patch (`dsh.bundle.patch`).
- `lib/task.js`: the task model. Statuses `next`, `now`, `waiting`, `done` and `dropped`; `done` and `dropped` are closed, so they block nothing. Fields it does not know are kept.

Only full `http(s)` URLs link, unless the caller passes `links` URL patterns (`{ref}`, `{repo}`, `{number}`).
- `lib/tree.js`: the tree text, led by a Problems block and ended by the Inbox block ("Inbox (1 open):", one line per item). Bad data never moves a row.
- `lib/inbox.js`: the Inbox model, no imports, inlined into the client bundle: states (`open`, `refined`, `dropped`), fields, ids, the default board key, the tree text's block, the strip's "N in inbox" and the text the tab's buttons fill.
- `skills/cockpit-refine.md`: the refine skill's instructions. `{{refineSkill}}` is replaced with the configured default delegate, or a line saying there is none.
- `skills/cockpit-process.md`: the process discovery skill instructions for mapping project workflow.
- `skills/cockpit-delegate.md`: the delegation skill (`delegateSkill()` in `index.js`, registered with the other two). Coordinator rules for the rest of the conversation: delegate all work with DSH's `subagent` tool, reuse one subagent per line of work through `send_message` (`list_agents` before starting a new one), record delegates on the board, end the turn instead of waiting, verify reports, relay questions, and ask the user when delegation is refused instead of working silently. It is guidance only: nothing enforces it, and it changes no tool. It names DSH's tool names (`subagent`, `send_message`, `list_agents`, `interrupt_agent`); a test checks they are in it.
- `lib/process.js`: process map storage, validation and YAML serialization for `.dsh/cockpit/process.yml`.
- `lib/store.js`: `$DSH_HOME/data/dsh-cockpit/boards/<encodeURIComponent(key)>.json`, format `dsh-cockpit.board`, version 1, written by temp file, fsync, rename and directory fsync. A file it cannot read is never overwritten. `revision` counts changes to tasks or to the board's parent; a write that changes neither, such as a report-only drift result, does not bump it.
- `lib/drift.js`: the drift runner and record. It keeps only the entries whose status differs from their task's, and `checked` counts every entry.
- `examples/board-drift-gh.sh`: an example drift command (see Drift runner).
- `reader.js` (`@rs-dsh/dsh-cockpit/reader`): `listBoards(dir?)`, `readBoard(keyOrFile, dir?)` and `boardTree(board)`, with no DSH imports. A miss names the folder it looked in and where `DSH_HOME` came from.
- `board.schema.json`: the file format as a JSON Schema, also for a local file that a hub without the plugin writes and the reader reads the same way; that file is never the plugin's own store.

## Actor vocabulary

Tool descriptions and examples use `user` for the person interacting with the assistant, not a project-ownership title. `waitsOnUser` recognizes `user` and the legacy `owner` alias, ignoring case and surrounding whitespace, in both host context and browser rendering. Board files remain lossless on read. Process validation normalizes legacy `who: owner` to `who: user` on read, propose and save; new tool schemas advertise only `user`. GitHub repository-owner references and DSH connection access-control terminology are unrelated.

## Config

```yaml
- id: dsh-cockpit
  name: '@rs-dsh/dsh-cockpit'
  config:
    tools: { enabled: true }      # false: register no tools
    route: { enabled: true }      # false: no routes, so no panel data
    drift: { command: '', cwd: '', mode: report }   # mode: report | apply; empty command: no check
    links: { issue: '', pr: '' }  # URL patterns with {ref}, {repo}, {number}; empty: only full URLs link, in the Board tab too
    planning: { enabled: true }   # false: no rule to plan multi-step work on a board; the upkeep rules stay
    inbox: { refineSkill: '', sendOnClick: true }    # refineSkill: the skill cockpit-refine delegates to by default (empty: its checklist); sendOnClick: the Inbox buttons queue their request instead of only filling the box
```

A profile patch with the same id replaces the whole config. A field it leaves out takes its default above, so a field it means to keep at a non-default value must be restated. The README shows the patch for GitHub links.

## Drift runner

Drift is a task whose status no longer matches its linked work, such as a merged PR on a task that still says `waiting`. The plugin knows no tracker, so the check is a command you configure in `drift.command`. With no command, nothing runs.

- **When.** Only on `board_read({ checkDrift: true })`. The command comes only from the profile config; no tool argument names it, and nothing runs on a timer.
- **How.** Through the system shell, in `drift.cwd` (empty: the host's directory), with the host's environment plus `DSH_HOME`, `DSH_COCKPIT_KEY` and `DSH_COCKPIT_FILE`, and the board's JSON on stdin. It runs in its own process group, so cancelling the call stops it and what it started (on Windows, only the shell). It runs outside the board's write queue, so other writes go on meanwhile; its result is then compared with the board as it is when stored.
- **Output.** `{ "items": [ { "item", "status"?, "note"? } ] }` on stdout. The board's `drift` keeps only the entries whose status differs from their task's, plus `checked`, the number of entries reported, and `checkedAt`. A non-zero exit or output that is not JSON stores `drift.error` instead, and the tasks stay as they were.
- **`drift.mode`.** `report` (the default) changes no task and does not bump `revision`; the hub decides and writes. `apply` sets each differing task's status and bumps `revision`.
- **Shown.** The tree text ends a row whose status still differs with "reported: done".

`examples/board-drift-gh.sh` is an example to copy and change. It reports `done` for each open task whose `pr` `gh pr view` reports as merged, and needs `gh` and `jq`; it fails when either is missing or gh can read none of the PRs. The plugin never runs it unless you name it in `drift.command`, for example `drift: { command: 'bash /path/to/board-drift-gh.sh', cwd: '/path/to/repo', mode: report }`.

## Installing from git

A profile can install the package from this repository with a git pin to the release tag:

```sh
dsh plugin --profile <name> add 'github:romany-saad/dsh-plugins#dsh-cockpit@<version>&path:packages/dsh-cockpit'
```

```json
"@rs-dsh/dsh-cockpit": "github:romany-saad/dsh-plugins#dsh-cockpit@<version>&path:packages/dsh-cockpit"
```

- **The tag works.** pnpm accepts a tag that contains `@` before `&path:`, and the lockfile records the tag's commit (`codeload.github.com/romany-saad/dsh-plugins/tar.gz/<commit>#path:packages/dsh-cockpit`). This was tried with pnpm 12.14.0 and `dsh plugin add` (DSH 0.2.1-rc.2) against a test tag. To pin a commit instead, put the commit in place of the tag: `#<commit>&path:packages/dsh-cockpit`.
- **The peers** `@deepseek-ai/dsh-tools` and `@deepseek-ai/dsh-home-paths` come from the DSH that boots the profile. pnpm may warn that they are missing from the profile itself.

## Releases

A release bumps `version` in `package.json`, adds a CHANGELOG entry and is tagged `dsh-cockpit@<version>` after the merge; pushing the tag publishes it to npm. npm shows the README of the last published version, so a README change reaches npmjs.com only with a release.
